# 06. 基于文档的开发循环

每轮只解决一个可验证目标：先确定文档契约和验收条件，再实现最小变更，最后用证据更新状态。开发者或 Agent 是执行者；需要业务取舍或额外操作授权时由用户确认。流程不依赖专门的任务服务、自动提交或常驻 Agent。

## 1. 最小记录结构

| 文件 | 记录什么 | 何时更新 |
| --- | --- | --- |
| 根 `README.md` | 项目入口、当前可用方式 | 使用方式或可用能力变化时 |
| [方案索引与 01–04](./README.md) | 系统行为、边界、接口和流程 | 契约变化时，先于依赖该变化的实现 |
| [05. 验收与交付](./05-validation-and-delivery.md) | 稳定验收场景及发布门槛 | 新增或改变行为时 |
| [STATUS.md](./STATUS.md) | 当前任务、状态、证据、阻塞与下一步 | 开始、交接、阻塞或完成一轮时 |
| 本文件 | 循环步骤与完成条件 | 开发方式确实改变时 |

状态只在 `STATUS.md` 维护，不为每轮复制一套 plan、tasks、report 或 checklist。接口细节仍写回原契约位置；任务记录只链接定义，不复制规格。代码和测试是实际行为的证据，文档是目标契约，两者不一致时先明确差异，不以任何一方自动覆盖另一方。

## 2. 一轮怎么执行

| 步骤 | 执行动作 | 结束条件 |
| --- | --- | --- |
| 1. 接续 | 查看 `git status --short`、相关差异和 STATUS，识别已有用户改动 | 当前任务、授权范围、已有工作及未完成项明确 |
| 2. 定义 | 在 STATUS 写入目标、范围、契约链接、验收 ID 或文档检查项 | 成功和失败结果可判断，影响结果的疑点已解决 |
| 3. 对齐 | 按方案索引核对契约；需要改行为时先改权威文档和验收条件 | 实现无需猜测边界、错误处理或输入输出 |
| 4. 实现 | 编写最小实现和对应测试；修复缺陷时先构造能证明问题的回归检查 | 范围内变更完成，相关失败路径有检查手段 |
| 5. 验证 | 按第 5 节向独立子智能体交接验证任务，由验证者运行检查、读取最终差异并回报结果；实现者修复失败项 | 验证者回报的必需检查全部通过，结论能定位到验证范围，验证者已记录 |
| 6. 回写 | 记录结果、局限和下一步，更新使用说明与任务状态 | 另一位执行者可从台账继续，不依赖聊天记忆 |

纯文档任务的第 4 步是文档修改，第 5 步检查链接、命令示例、术语和跨文档一致性；不创建空程序来满足流程。解释问题无需进入开发循环。

验收矩阵已有场景时引用其 ID。新增可观察行为而矩阵未覆盖时，先新增稳定 ID；仅调整排版或导航时可在任务中列文档检查项，不扩大产品测试矩阵。

## 3. 状态与推进

```text
待开始 → 进行中 → 待验收 → 已完成
             ↑       |
             └─ 验证失败
进行中 / 待验收 → 阻塞 → 进行中
```

| 状态 | 判定 |
| --- | --- |
| 待开始 | 已记录候选任务，尚未开始；候选任务本身不构成授权 |
| 进行中 | 执行范围已明确，正在对齐契约、实现或修复验证失败 |
| 待验收 | 修改已完成，仍有本轮必需检查未完成 |
| 阻塞 | 缺少明确决策、权限或环境，无法完成当前必需步骤；写明解除条件 |
| 已完成 | 满足下一节的全部完成条件 |

默认同一时间只有一个「进行中」或「待验收」任务；明确要求并行时才拆分互不冲突的范围，并分别记录负责人和依赖。已完成任务出现新问题时创建关联修复任务，不抹去原验收事实。

检查失败先修复当前任务，不顺手扩展功能。涉及格式兼容、数据丢失、凭据继承、外部访问或平台支持的未决问题，暂停依赖该结论的部分并询问具体选项；无关任务仍可按授权推进。

一轮完成后只提出下一项建议。用户只授权当前任务时，不自动从台账继续实现后续功能；提交和推送也分别需要明确授权。

## 4. 完成条件

- 本轮范围内的目标都有对应实现或文档结果，没有静默删掉失败场景以通过检查。
- 涉及的契约、示例、目录说明和验收条目相互一致；源码新增目录有实际职责，不为空未来功能提前铺设抽象。
- 必需验证全部通过，并按第 5 节由独立子智能体执行；记录验证者、验证日期、环境、命令或可复核步骤、结果及对应验收 ID；未运行的检查写明原因，不填「通过」。
- 最终差异包含新建和未跟踪文件，未覆盖用户的无关修改，未混入凭据、真实记忆、缓存或生成产物。
- STATUS 记录遗留限制和下一步。功能完成、平台通过与发布就绪分别判断，不从单项测试推导整个阶段完成。

环境缺失导致必需测试无法运行时，任务保持「待验收」或「阻塞」，说明已完成的修改和缺少的证据。对本轮不适用的检查说明理由即可，例如纯文档任务不运行二进制测试。若要缩小本轮范围，先明确说明影响；不能在回写状态时偷偷改变完成条件。

## 5. 验证如何落地

验证由独立子智能体（下称验证者）执行，即验证者不参与本轮实现，实现者不判定本轮通过。实现者向验证者交接验证任务，任务至少包含以下内容。

| 交接项 | 内容 |
| --- | --- |
| 范围 | 本轮改动的文件、受影响的契约和验收 ID |
| 检查 | 需要运行的命令、需要读取的最终文件与差异 |
| 预期 | 每项检查的通过条件，以及失败时应报告的证据 |
| 约束 | 验证过程只读工作区，不修改文件、不暂存、不提交 |

验证者独立运行检查，回报原始输出与逐项结论；结论写入 `STATUS.md` 时同时记录验证者标识。验证发现的问题由实现者修复，修复后重新交接验证。实现者自己运行的检查只用于排查，不作为完成证据。

子智能体不可用、交接失败或验证未覆盖必需范围时，本轮保持「待验收」或「阻塞」，写明已完成的修改和缺少的证据，不得由实现者补做检查并标记完成。

| 变更类型 | 最小验证 |
| --- | --- |
| 文档和导航 | 本地链接与锚点、示例语法、权威定义一致性、最终差异 |
| 格式或领域逻辑 | 对应单元测试、无损保真样例和错误输入 |
| Git、锁和文件写入 | 临时仓库集成测试、冲突与中断场景；使用 05 中相关 ID |
| CLI、HTTP 和 Hook | 参数、输出、错误码、版本条件、鉴权及回归 |
| 平台、后台和凭据 | 目标平台实际运行；交叉编译不替代生命周期与非交互认证测试 |
| UI | 构建及协议检查；仅在用户明确要求时验证 UI/UX 效果，未验证的视觉交互如实记录 |

使用仓库已经存在的测试入口。当前没有 Go 或前端工程时，不执行方案示例中的构建命令并宣称通过。首次建立工具链的任务同时提供真实入口和可复现说明；后续直接引用该入口，不在多处复制命令清单。

测试环境遵循 [验收与交付](./05-validation-and-delivery.md) 的隔离要求。临时仓库、日志和调试脚本放在工作区外；可复用的合成 fixture 放入 [目录规划](./01-architecture-and-modules.md#5-目录结构与依赖) 指定位置。平台或阶段的汇总结果较多时才创建 `docs/validation/` 保存报告，由 STATUS 链接；普通任务保留一条可复核记录即可。

`git diff --check` 只能检查已进入差异的内容，不能替代新建文件检查。未跟踪文件逐项纳入阅读和验证；不要为了得到 diff 而自动暂存用户文件。

## 6. 交接与中断

停止前写明当前状态、已改文件、已跑检查、失败点和下一步。发现用户同时修改同一目标时先对齐冲突，不用旧草稿覆盖新内容。

接续时以工作区实际文件核验台账；若台账与磁盘不一致，先记录差异再继续。临时目录或聊天输出可以辅助排查，但不能作为长期唯一验收依据。任务历史保留结果摘要，不保留逐条终端输出或重复的推理过程。
