# 06. 基于文档的开发循环

按照开发计划持续推进，每个会话完成一轮可验证任务：先读取项目约定、开发计划和最新进度，核对完整剩余事项及其依赖，明确本轮范围与验收标准；再完成实现、验证、返修与文档同步；验证通过后更新台账、提交并推送远端，按剩余计划在同一本地工作区创建新会话接续下一轮。默认由主会话完成本轮全流程并保留整轮验收与交付责任，按需使用子智能体。用户最新的停止、暂停或范围调整指令优先执行。

## 1. 最小记录结构

| 文件 | 记录什么 | 何时更新 |
| --- | --- | --- |
| 根 `README.md` | 项目入口、当前可用方式 | 使用方式或可用能力变化时 |
| [方案索引与 01–04](./README.md) | 系统行为、边界、接口和流程 | 契约变化时，先于依赖该变化的实现 |
| [05. 验收与交付](./05-validation-and-delivery.md) | 阶段开发计划、稳定验收场景及发布门槛 | 新增或改变行为、调整阶段计划时 |
| [STATUS.md](./STATUS.md) | 当前事实、任务总表、最近 1 轮完成记录、近期待办与下一步 | 开始、交接、阻塞或完成一轮时 |
| `docs/validation/` | 按交付阶段归档的历史任务验收记录（如 `stage-a.md`）与阶段/平台报告 | 新一轮完成并将更早完成记录从 `STATUS.md` 归档时 |
| 本文件 | 循环步骤、职责边界、完成条件与跨会话接续规则 | 开发方式确实改变时 |

`STATUS.md` 作为热台账只保留当前事实、任务总表（含归档锚点链接）、最近 1 轮完成记录和近期实施任务定义；早于最近 1 轮的已完成任务记录按交付阶段移入 `docs/validation/stage-<x>.md`，由任务总表直接链接，防止 `STATUS.md` 随轮次膨胀并避免每轮复制 plan、tasks、report 或 checklist。

单条完成记录只保留最小可复核结构（目标与范围、契约链接、验证环境与命令、通过的验收 ID 与结论、未运行项与遗留限制），不记录多轮返修往返、验证者提示过程或逐条终端输出等过程噪声。接口细节写回原契约位置；任务记录只链接定义，不复制规格。代码和测试是实际行为的证据，文档是目标契约，两者不一致时先明确差异，不以任何一方自动覆盖另一方。

## 2. 一轮怎么执行

| 步骤 | 执行动作 | 结束条件 |
| --- | --- | --- |
| 1. 接续 | 读取 [协作入口](../AGENTS.md)、[阶段计划](./05-validation-and-delivery.md#1-交付顺序)、`STATUS.md` 与 `git status --short`，核对完整剩余事项及其依赖，识别共享工作区已有改动 | 剩余事项与依赖、本轮范围及工作区现状明确 |
| 2. 定义 | 在 `STATUS.md` 写入本轮目标、范围、契约链接、验收 ID 或文档检查项 | 本轮范围与验收标准可判断，影响结果的疑点已解决 |
| 3. 对齐 | 按 [方案索引](./README.md) 核对契约；需要改变行为时先更新权威文档和验收条件 | 实现无需猜测边界、错误处理或输入输出 |
| 4. 实现 | 默认由主会话编写最小实现和对应测试；修复缺陷时先构造回归检查；满足第 5 节条件时可按需委派子智能体 | 范围内变更完成，相关失败路径有检查手段，共享工作区中的他人改动已保留 |
| 5. 验证 | 运行本轮检查、测试与必要回归，审阅最终差异；验证失败时先在本轮返修并重验 | 必需检查全部通过，结果能定位到验证范围；未将失败轮次标记为完成 |
| 6. 交付与接续 | 确认子智能体（若使用）全部已结束；同步更新 `STATUS.md`、将上一轮完成记录归档至 `docs/validation/`、更新相关文档，提交并推送远端；按第 6 节选择下一轮并创建新会话或停止接续 | 台账、归档与远端已同步；新会话已创建且旧会话结束开发，或已按停止条件说明原因 |

纯文档任务的第 4 步是文档修改，第 5 步检查链接、命令示例、术语和跨文档一致性；不创建空程序来满足流程。只回答问题时按需查阅文档，不进入开发循环。

验收矩阵已有场景时引用其 ID。新增可观察行为而矩阵未覆盖时，先新增稳定 ID；仅调整排版或导航时可在任务中列文档检查项，不扩大产品测试矩阵。

## 3. 状态与推进

```text
待开始 → 进行中 → 待验收 → 已完成
             ↑       |
             └─ 验证失败
进行中 / 待验收 → 阻塞 → 进行中
```

| 状态 | 判定 |
| --- | --- |
| 待开始 | 已列入计划但尚未开始；核对剩余计划与前置依赖后择优进入下一轮 |
| 进行中 | 本轮范围与验收标准已明确，正在对齐契约、实现或返修验证失败项 |
| 待验收 | 修改已完成，仍有本轮必需检查或子智能体核验未完成 |
| 阻塞 | 缺少明确决策、必要权限或外部条件，无法完成当前任务必需步骤；写明解除条件 |
| 已完成 | 满足第 4 节的全部完成条件 |

每个会话只完成一轮任务，默认同一时间只有一个「进行中」或「待验收」任务。已完成任务出现新问题时创建关联修复任务，不抹去原验收事实。

用户最新的停止、暂停或范围调整指令优先执行。验证失败时必须先在本轮返修并重新验证，不顺手扩展无关功能，也不得将失败轮次标记为「已完成」。

局部外部依赖受阻，或涉及格式兼容、数据丢失、凭据继承、外部访问、平台支持等仅影响局部任务的未决问题时，将该任务记为「阻塞」并写明解除条件；局部受阻不自动阻断其他前置条件已满足的独立任务。

满足以下任一停止条件时，停止跨会话自动接续并向用户说明原因：

- 总计划中的全部任务均已完成。
- 存在需要用户决策且会影响结果的未决问题。
- 核对完整剩余计划后，确认缺少必要条件且没有任何可执行任务。

## 4. 完成条件

- 本轮范围内的目标都有对应实现或文档结果，没有静默删掉失败场景以通过检查。
- 涉及的契约、示例、目录说明和验收条目相互一致；源码新增目录有实际职责，不为未来功能提前铺设空抽象。
- 必需验证全部通过。记录验证日期、环境、执行者（主会话或按需委派的子智能体）、命令或可复核步骤、结果及对应验收 ID；未运行的检查写明原因，不填「通过」。
- 若本轮使用了子智能体，必须确认全部子智能体已结束，且主会话已完成结果复核与整轮验收。
- 最终差异包含新建和未跟踪文件，保留共享工作区中的他人改动，未混入凭据、真实记忆、缓存或生成产物。
- `STATUS.md` 已按第 1 节同步更新当前进度与最近一轮完成记录，更早完成记录已按阶段归档至 `docs/validation/`；本轮变更已提交并推送远端（用户明确指示不提交或不推送时除外，并在台账说明）。功能完成、平台通过与发布就绪分别判断，不从单项测试推导整个阶段完成。

环境缺失导致必需测试无法运行时，任务保持「待验收」或「阻塞」，说明已完成的修改和缺少的证据。对本轮不适用的检查说明理由即可，例如纯文档任务不运行二进制测试。若要缩小本轮范围，先明确说明影响；不得在回写状态时静默放宽完成条件。

## 5. 验证如何落地

默认由主会话完成本轮实现、检查、返修、文档同步和交付，主会话保留整轮验收与交付责任。满足以下任一条件时，可按需使用子智能体：

- 存在边界清晰、可独立推进的工作。
- 复杂数值、协议或安全边界需要第二个独立检查视角。
- 大量调查上下文需要与主会话隔离。

委派子智能体前，主会话先说明预期收益，并明确交接以下内容：

| 交接项 | 内容 |
| --- | --- |
| 任务与范围 | 子智能体需完成的调查、实现或检查目标，以及受影响的契约与验收 ID |
| 文件所有权 | 允许修改的文件范围（或只读约束）；必须保留共享工作区中的他人改动，不暂存、不提交未授权文件 |
| 验收条件 | 交付物或检查通过标准，以及失败或异常时应回报的原始证据 |

子智能体完成后向主会话回报结果与证据；若用于第二视角检查或协助验证，`STATUS.md` 同时记录子智能体标识与结论归属。验证发现的问题由主会话（或负责该范围的子智能体）在本轮返修并重新验证；主会话不得在子智能体尚未结束或必需检查未通过时将本轮标记为「已完成」。

| 变更类型 | 最小验证 |
| --- | --- |
| 文档和导航 | 本地链接与锚点、示例语法、权威定义一致性、最终差异 |
| 格式或领域逻辑 | 对应单元测试、无损保真样例和错误输入 |
| Git、锁和文件写入 | 临时仓库集成测试、冲突与中断场景；使用 05 中相关 ID |
| CLI、HTTP 和 Hook | 参数、输出、错误码、版本条件、鉴权及回归 |
| 平台、后台和凭据 | 目标平台实际运行；交叉编译不替代生命周期与非交互认证测试 |
| UI | 构建及协议检查；仅在用户明确要求时验证 UI/UX 效果，未验证的视觉交互如实记录 |

使用仓库已经存在的测试入口。当前没有 Go 或前端工程时，不执行方案示例中的构建命令并宣称通过。首次建立工具链的任务同时提供真实入口和可复现说明；后续直接引用该入口，不在多处复制命令清单。

测试环境遵循 [验收与交付](./05-validation-and-delivery.md) 的隔离要求。临时仓库、日志和调试脚本放在工作区外；可复用的合成 fixture 放入 [目录规划](./01-architecture-and-modules.md#5-目录结构与依赖) 指定位置。历史任务验收记录与阶段/平台报告按第 1 节归档至 `docs/validation/` 并由 `STATUS.md` 链接。

`git diff --check` 只能检查已进入差异的内容，不能替代新建文件检查。未跟踪文件逐项纳入阅读和验证；不要为了得到 diff 而自动暂存用户文件。

## 6. 交接与中断

本轮验证通过、确认全部子智能体已结束、更新 `STATUS.md` 并完成提交和推送后，按完整剩余计划及其依赖选择下一轮任务：

- 存在可执行任务且未触发第 3 节停止条件时，无需询问是否继续，直接在当前项目的同一本地工作区创建新会话发起下一轮。
- 新会话创建成功后，旧会话立即结束开发，禁止在旧会话继续修改文件或开启下一轮，避免并行修改。
- 新会话创建失败时，保留完整交接信息并向用户说明失败原因，禁止在旧会话中开始第二轮任务。

发起下一轮时，新会话初始提示词应详略得当、控制长度，并完整包含以下内容：

| 交接项 | 内容 |
| --- | --- |
| 有效规则与边界 | 当前有效的自动接续规则、主会话与子智能体职责、模型选择和权限边界 |
| 本轮结果与证据 | 本轮完成结果、提交与推送状态、关键验证证据及未解决问题 |
| 剩余事项与依赖 | 完整剩余事项清单、各自前置依赖与当前阻塞项 |
| 下一轮目标 | 下一轮任务目标、范围、验收条件及选择依据 |

因停止条件、用户指令或异常中断时，停止前写明当前状态、已改文件、已跑检查、失败点或阻塞原因及下一步。接续工作时以工作区实际文件和 `git status` 核验 `STATUS.md`；若台账与磁盘不一致，先记录并对齐差异再继续，不用旧草稿覆盖共享工作区中的他人改动。临时目录或聊天输出只用于辅助排查，不能作为长期唯一验收依据。任务历史保留结果摘要与可复核证据，不保留逐条终端输出或重复的推理过程。
