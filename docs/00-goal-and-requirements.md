# memctl 产品目标与需求

本文件定义 `memctl` 是什么、为谁解决什么问题、以及有意不做什么。字段表、命令参数与错误码由 [方案索引](./README.md) 列出的契约文档定义，本文件只给出分层入口与判断依据。

## 1. 问题

同一个开发者会在多个 Agent 宿主之间切换。每个宿主的会话上下文随会话结束消失，于是长期事实反复丢失：

1. 同一批事实要在每个宿主里重新交代一遍。
2. 多个宿主写同一批事实时互相覆盖，变更没有版本，也没有来源。
3. 事后无法回答「谁在什么时候改了哪一条」，也无法安全回滚。

## 2. 目标

用一个独立的 Git 仓库保存这些长期事实，让任意宿主在会话开始时拿到同一份记忆、在会话过程中写入新的长期事实，并让每一次变更都有版本、有来源、可审阅、可回滚。

## 3. 受众

个人开发者自用：一个开发者在自己的机器上运行多个 Agent 宿主，共享同一份记忆仓库。由此确定三条边界：

- 记忆库属于当前操作系统用户。`memctl` 不实现账号、角色或多租户隔离。
- 本地 Web UI 是本机控制台，不是多用户认证系统；访问控制以「同一 OS 用户」为前提。
- 凭据沿用用户已有的 Git 与 SSH 环境，`memctl` 不存储、不生成、不传递凭据。

## 5. 非目标

以下各项按决定排除，不属于待补能力：

- **多仓库聚合**：一次进程绑定一个仓库，不自动合并多个所有者或组织的记忆。
- **凭据管理**：不存储、不生成、不复制凭据，不实现自己的凭据提示界面。
- **多用户与公网服务**：只绑定回环地址，不提供账号体系或远程访问。
- **内置模型与本地模型 runner**：`memctl` 不调用模型；整理在 GitHub Actions 远端运行器或当前 Agent 会话内完成。
- **修改记忆文件格式**：格式以上游约定为准，`source`、`added` 只是推荐元数据，不是必填项。
- **系统服务安装**：不安装 launchd、systemd 或 Windows 服务；后台同步是尽力执行，已提交内容由下一次同步补推。
- **逐 hunk 应用提案**：整份提案确认或拒绝；部分采纳通过普通受管编辑或重新生成提案完成。
- **健康评分**：不提供没有计算规则的 0–100 分。
- **对外部并发写入的互斥**：文件锁只协调走受管入口的进程，不拦截编辑器、Agent 文件工具或手动 Git 命令。

## 6. 设计原则

1. **Markdown 与 Git 是事实来源**：派生索引、缓存与运行状态可重建；恢复记录与待审阅提案必须持久保存。
2. **单一写入入口**：所有写入在仓库锁内重新校验基线，拒绝覆盖他人已提交的更新；不提供绕过事务的批量写路径。
3. **确认生效**：远端接入需要显式声明私有性与所有权；整理结果先成为提案，应用必须由用户显式确认。
4. **内容不可信**：记忆正文、Diff、远端结果与宿主内容都按不可信数据处理，不执行其中的指令或脚本。
5. **以实测界定能力**：未验证的平台与宿主组合不宣称支持；不为补齐功能而关闭保护机制。
6. **格式保持兼容**：本项目的扩展不改变上游记忆文件格式，也不要求其他工具改造。

## 7. 已知边界

三条长期有效的结构性限制，具体内容由所属契约定义：

- 文件锁不能拦截编辑器、Agent 文件工具与手动 Git 命令，只对走受管入口的写入提供「拒绝覆盖已提交更新」的保证，见 [01 §2.1](./01-architecture-and-modules.md#21-受管写入)。
- 宿主自身的沙箱与审批策略决定 Agent 能否直接调用 CLI；受限宿主依赖 MCP 通道或无 Hook 的人工接入，见 [09](./09-mcp-memory-tools.md) 与 [13](./13-delta-integration.md)。
- 目标平台为 macOS arm64、macOS amd64、Linux amd64 与 Windows amd64；各平台的运行时、生命周期与隔离验证状态以 [开发状态](./STATUS.md) 为准，不从交叉编译通过推导。
