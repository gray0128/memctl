# 10. 记忆更新与过期：调研结论与生命周期规则

> 状态：调研完成（2026-10-19）；§7 的三个未决问题已于 2026-10-19 由用户确认，`until` 解析、读取期隐藏与三个入口的统一过滤已实现（`T094`）。删除任务仍未实现。本文档只定义记忆的更新、过期与删除规则；文件格式、写入事务与接口仍以 [02](./02-domain-models-and-contracts.md) 与 [03](./03-workflows-and-dataflows.md) 为准。

## 1. 结论

- 记忆按内容类型分三档处理：状态型就地改写或删除，事件型追加保留，有时效型带到期元数据。
- 默认删除过期记忆，但删除只作用于「注入与检索可见的当前内容」。历史由 Git 提交保存，不写进记忆正文。
- 不默认保留完整时间线。`MEMORY.md` 每轮注入，时间线会持续抬高每轮 Token 成本，并让模型同时读到互相矛盾的旧值。
- 同一事实不得有两条并存。更新是替换，不是追加一条「现在改为……」。
- 删除是破坏性操作。经 Dreaming 或 UI 发起时，必须出现在固定 Diff 里由用户确认，沿用已有的 `proposalId + patchHash` 流程。

判据：一次读取时，模型只应看到「当前成立的事实」；任何「当时成立」的信息必须能从 Git 或条目元数据单独查出来。

## 2. 调研结论

下表是本次调研的来源与观察，用于支撑第 1 节的规则。结论按项目归类，不构成对实现质量的评价。

| 项目 | 过期或冲突时的处理 | 历史保存在哪里 |
| --- | --- | --- |
| [Mem0](https://docs.mem0.ai/core-concepts/how-it-works) | 新算法改为单次 ADD-only 提取，不再自动 UPDATE/DELETE；纠正依赖显式 `update` 与 `delete` | [history 接口](https://docs.mem0.ai/api-reference/memory/history-memory)记录 ADD/UPDATE/DELETE 事件与 `old_memory`；正文只保留当前值 |
| [Mem0 过期](https://docs.mem0.ai/platform/features/memory-expiration) | 到期只隐藏、不删除；`decay` 只调整排序；`delete` 才是永久删除 | 三者语义分离：可逆隐藏、排序衰减、永久删除 |
| [Zep 事实](https://help.getzep.com/v4/facts) | 新事实使旧事实失效而非删除，保留 `created_at`、`valid_at`、`invalid_at`、`expired_at` 四个时间戳 | 双时间模型加 episode 原始出处，支持时点查询 |
| [Zep 图构建](https://help.getzep.com/v4/how-graph-creation-works) | 矛盾事实使旧事实失效，不允许互相矛盾的两条并存 | 同上 |
| [Zep 保留策略](https://help.getzep.com/v4/context-retention) | 默认不按时间过期；过期需显式配置 `retain_for`，先 `report_only` 再 `enforce` | 删除永久、无撤销，只保留备份期内副本 |
| [Letta memory block](https://docs.letta.com/guides/agents/memory-blocks) | 更新为整体覆盖，last write wins，不追加 | 历史来自 [MemFS](https://docs.letta.com/concepts/memfs) 的 Git 仓库，每次编辑提交 |
| [LangMem](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/) | 明确二选一：collection 保留全部并可更新删除，profile 只保留当前状态 | 选型取决于是否需要历史 |
| [MemoryBank](https://arxiv.org/abs/2305.10250) | 按艾宾浩斯遗忘曲线，以时间和重要性决定遗忘与强化 | 遗忘是评分机制，不是删除记录 |
| [A-MEM](https://arxiv.org/abs/2502.12110) | 写入即演化：更新笔记属性并重建关联 | 演化过程留在笔记与链接中 |
| [Anthropic memory tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool) | 官方建议删除不再相关的内容，并定期清理长期未访问的文件 | 无内建时间线，依赖文件系统或实现方版本控制 |
| [Cognee forget](https://docs.cognee.ai/core-concepts/main-operations/forget) | 硬删并级联清理派生对象；`memory_only` 保留原始文件以便重建 | 原始文件加可重跑的处理管线 |

两条与本项目直接相关的经验：

- Mem0 从「模型决定 ADD/UPDATE/DELETE」收敛为 ADD-only，理由是让模型把容量用于理解输入而不是与旧状态做 diff。这说明「让模型自动判断该不该删」本身不可靠，删除应有确定性规则或人工确认。
- Zep 强调不能让矛盾的旧事实与新事实并存，否则检索会同时返回两条互相否定的结论。它用失效标记同时满足「不矛盾」和「可追溯」，而本项目用「改写当前条目 + Git 保存历史」达到同样效果。

没有任何一个调研对象默认保留完整时间线：需要历史时，它们要么依赖版本控制，要么依赖结构化时间戳字段，都不把时间线写进每轮加载的正文。

## 3. 记忆分类与处理规则

### 3.1 按内容类型分类

| 类型 | 典型内容 | 写入方式 | 过期处理 |
| --- | --- | --- | --- |
| 状态型 | 用户偏好、环境配置、当前角色、项目现状、命名约定 | 就地改写同一条目，或删除 | 直接改写或删除，不保留旧值 |
| 事件型 | 决策及其理由、发布、事故、迁移、为什么这样选 | 追加带日期的条目，只增不改 | 不按时间过期，长期保留 |
| 有时效型 | 试用期、临时约束、截止日期、季节性偏好 | 写入时带 `until: YYYY-MM-DD` | 到期后从注入与检索中隐藏，隐藏 30 天后再删除 |

分类依据是「事实失效后是否仍需要知道它曾存在」：需要则归为事件型，不需要则归为状态型。

### 3.2 更新规则

1. 更新状态型记忆时，替换原有条目，不新增一条描述变化过程的条目。
2. 同一事实在 `MEMORY.md` 与 `notes/` 中不得各存一份；一处定义，其余位置用 `[[path]]` 链接。
3. 判断某条记忆是否仍然成立时，不能仅凭字符串相似度去重；相似但矛盾的记忆保留来源并提请审阅。
4. 删除条目时，同一提交内更新指向它的 `[[path]]` 链接与 `MEMORY.md` 索引项。

### 3.3 过期规则

1. 过期不改变来源元数据。`source` 与 `added` 在条目存续期间保持原值。
2. 有时效型条目到期后先隐藏而不是删除：注入与检索过滤该条目，正文与 Git 历史保留。
3. 隐藏期为 30 天：到期后满 30 天，才允许由显式动作删除。隐藏期从 `until` 的次日开始计算。
4. 删除动作必须可追溯到发起者（用户、Dreaming 提案或 UI 操作）。
5. 事件型条目没有过期时间，删除只发生在用户明确要求或来源本身被撤回时。

### 3.4 判定与隐藏的落地口径

以下口径是实现与三个读取入口的共同依据，`T094` 已按此实现读取侧，删除侧仍待实现。

- **到期判定**：`until` 是 `YYYY-MM-DD` 本地日期，该日整天仍然可见；从次日本地零点起判为到期。`until` 缺失或不是合法日期时按永不过期处理，不产生诊断错误。
- **过滤位置**：在读取层统一过滤，三个入口看到同一结果。注入（`start`/`context`）、`read`/`memory_read`、`entries`/`memory_entries`/`GET /api/v1/entries` 与 Web UI 快照共用同一判定。
- **`read` 的返回形态**：完整文件读取保留行数与元数据，只把已到期条目的正文替换为固定占位符 `[已过期：…]`，并保留其 `until`/`source`/`added` 原文；响应附带 `hiddenExpired` 计数。这样读者知道「这里有一条被隐藏的条目」，写入基线仍是磁盘原文，不会因隐藏而删除数据。
- **结构化读取**：条目列表、快照与 MCP `memory_entries` 直接剔除已到期条目，不返回占位符；快照的 `hiddenExpired` 给出被剔除的总数，用于区分「没有条目」与「被过期隐藏」。
- **写入不变**：隐藏只作用于读取结果。写事务、基线校验、Git 提交与 `doctor` 都按磁盘原文工作；被隐藏的条目在下次写入时按原样保留。
- **删除入口**：隐藏期满 30 天后，删除仍须经 UI 单条删除或 Dreaming 提案（固定 Diff 确认），不在读取或注入路径上自动删除。

## 4. 当前实现边界

| 到期条目诊断 | `doctor` 以 `EXPIRED_ENTRY`（info）报告已隐藏的条目及其行号 | 已实现（`T094`）；不自动修复，不删除 |
| 时间线查询 | `git log -S` 与审计 Diff 接口可回答条目变更历史 | 不需要在正文维护 changelog |

## 5. 禁止项

1. 禁止在 `MEMORY.md` 中维护变更日志或「以前是……现在是……」的对照段落。
2. 禁止把已失效的状态型条目保留为「历史参考」；需要保留的情况必须归入事件型并写明日期。
3. 禁止用自动去重替代事实判断：字符串相同不等于事实相同，字符串不同也不等于事实冲突。
4. 禁止在没有用户确认的情况下批量删除条目；单条删除同样要出现在可复核的变更记录中。
5. 禁止为过期机制引入新的必填元数据：`source`、`added` 与新增的 `until` 都保持可选，缺失时按永不过期处理。

## 7. 已确认的决策与剩余问题

2026-10-19 由用户确认：

- **隐藏期长度**：30 天。到期后满 30 天才允许删除，删除仍是显式动作。
- **过滤位置**：三个读取入口统一过滤。注入、`read`/`memory_read` 与条目查询/快照使用同一判定；`read` 保留行并用占位符标注，结构化读取直接剔除。
- **事件型条目**：继续留在 `MEMORY.md` 与 `notes/`，不新增目录或索引项；事件条目增长到需要独立结构时再评估。

仍未决：

- 发现层面已有确定性检查：`doctor` 报告 `EXPIRED_ENTRY`（info）与 `MISSING_RECOMMENDED_METADATA`，但「疑似 changelog 条目」仍需先观察真实写入模式，暂不加入。
- 隐藏期满后的删除**闸门**已实现：任何入口删除已到期条目时都必须先满 30 天，否则返回 `DELETION_DEFERRED`。由哪个入口**发起**批量清理（UI 单条删除、`doctor --fix` 还是 Dreaming 提案）尚未确定；三者都能删除会分散追溯点，倾向由 Dreaming 提案统一发起。
